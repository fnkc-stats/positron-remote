**1. Высокий — шлюз SSH разрешает доступ к любому TCP-сервису на loopback. Подтверждено.**

Источник: [admin.ts](../ctl/src/admin.ts), `authorizedKeysLine`, строка 40; [install.sh](../ctl/server/install.sh), строки 53–70.

`restrict,port-forwarding,permitopen="127.0.0.1:*"` разрешает подключения ко всем TCP-портам loopback хоста, а не только к контейнеру запрашивающего пользователя. Принудительная команда ограничивает выполнение команд; каналы переадресации не проходят через `Agent.own()`. Для других контейнеров по-прежнему нужны их собственные SSH-ключи, но база данных, отладочная точка, панель мониторинга или API Docker на loopback могут рассчитывать на другую аутентификацию. Тест достучался до имитации TCP-сервиса именно с этой политикой ключа.

Установщик также не требует, чтобы TCP-переадресация была только локальной. Поэтому обратная переадресация зависит от существующей конфигурации хоста. Последствия зависят от развёрнутых сервисов и настроек sshd; это не доказательство продемонстрированного захвата хоста.

Исправление: явно настроить служебную учётную запись с `AllowTcpForwarding local` и `AllowStreamLocalForwarding no`, затем заменить шаблон точными разрешёнными точками для каждого пользователя. Для этого нужно выделение и авторизация точек под управлением root или прокси соединений с проверкой владельца. Установка должна завершаться ошибкой, если действующие ограничения несовместимы. Проверить, что обычный ProxyJump работает, а посторонние порты, точки других пользователей и обратная переадресация запрещены. Эти механизмы описаны в [ограничениях ключей OpenSSH](https://man.openbsd.org/sshd.8) и [конфигурации sshd](https://man.openbsd.org/sshd_config).

**2. Высокий — то, что ИИ-автор не видит данных, не делает безопасным запуск его кода на данных. Риск запланированной архитектуры.**

Источник: [README](../README.md), строки 206–211; [meeting-summary.md](../meeting-summary.md). CI-конвейер для чувствительных данных — предложение, а не существующий workflow.

Предложенная последовательность: агент пишет код R/Quarto без данных; CI в PR расшифровывает реальные данные и выполняет этот код. Код всё равно может прочитать каждую переданную запись и поместить её в HTML, логи, артефакты или исходящие запросы. Одно лишь отключение исходящего трафика не мешает раскрытию через отрендеренный отчёт. Контейнер не отличает задуманный анализ от непреднамеренной выгрузки данных.

Исправление: автоматические проверки PR запускать на синтетических данных без секретов. Задания на реальных данных запускать только для проверенного неизменяемого коммита на отдельном одноразовом раннере. Использовать доверенное определение workflow, входные данные только для чтения, процесс без root, ограниченный доступ к сети и без сокета Docker. Результаты и логи держать под контролем доступа; проверять результаты перед более широкой публикацией. Следующие коммиты должны аннулировать согласование. Для уведомлений отправлять ссылки на отчёты с аутентификацией, а не публичные отчёты или встроенные чувствительные результаты. Общий принцип разделения недоверенного кода и секретов описан также в [рекомендациях GitHub по безопасности workflow](https://docs.github.com/en/actions/reference/security/secure-use); конкретная реализация здесь должна подходить для Gitea.

**3. Высокий — окружение не является ни неизменяемым, ни надёжно связанным с анализируемым кодом. Статические замечания.**

Источник: [validate.ts](../ctl/src/validate.ts), строки 46–59; [env-image.yml](../.github/workflows/env-image.yml), строки 26–50; [project.ts](../ctl/src/client/project.ts), строки 53–78; [open.ts](../ctl/src/client/open.ts), строки 67–90; [fnkc-projects.sh](../ctl/container/fnkc-projects.sh), строки 67–83.

Валидатор явно отклоняет дайджесты. Тег из даты и коммита всё равно изменяем: повторный запуск в тот же день на том же коммите публикует тот же тег, в том числе при смене платформ. Сборка использует изменяемый тег базового образа Rocker и текущие репозитории apt. Агент скачивает образ, только если его нет локально, поэтому на двух машинах под одним тегом может остаться разное содержимое. Отпечаток по ID образа обнаруживает локальные изменения, но не изменения только в реестре. [Docker описывает дайджесты как неизменяемые идентификаторы образов](https://docs.docker.com/reference/cli/docker/image/pull/).

Кроме того, клиент читает `container.json` из удалённого `HEAD` до подключения к постоянной рабочей копии. Эта рабочая копия может быть на более старом коммите, на ветке функции или содержать правки. Sync намеренно сохраняет такие состояния. Например, в main образ меняется с A на B, а аналитик на ветке, которой нужен A: повторное открытие может заменить контейнер на B, сохранив старую ветку. Даже первое клонирование может разойтись с новым удалённым коммитом между получением метаданных и клонированием.

Исправление: поддержать и требовать разрешённые дайджесты образов; понятные теги публиковать как метки для удобства. Использовать уникальные идентификаторы сборок и записывать архитектуру плюс дайджест манифеста/платформы. Определять ревизию репозитория и её окружение вместе. Существующие проекты должны использовать манифест фактической рабочей копии; новые проекты — клонировать точный найденный коммит. Изменения ветки или окружения делать видимыми и явными. С каждым отчётом записывать коммит кода, наличие незакоммиченных изменений, дайджест образа, версию/хеш данных, параметры и seed генератора случайных чисел. Не использовать незаметно образ по умолчанию для рабочих проектов.

**4. Высокий — открытие проекта может принудительно уничтожить активную сессию. Статическое замечание.**

Источник: [agent.ts](../ctl/src/agent.ts), строки 73–92.

Любое изменение отпечатка настроек вызывает `docker rm -f`, включая изменения образа, ключа, ограничений, настроек простоя и встроенных скриптов. Нет ни проверки работающих заданий, ни плавной миграции. Второй клиент, открывающий тот же проект, может убить идущий расчёт R. Подключённые файлы сохраняются, но память R, незаконченные результаты и файлы вне подключённых каталогов — нет.

Исправление: различать переподключение и обновление. Переподключаться к уже работающему окружению и сообщать об ожидающем обновлении; применять изменения после остановки или после явного действия «обновить с прерыванием». Сохранять предыдущий остановленный контейнер, пока инициализация замены не завершится успешно. Для отзыва доступа по соображениям безопасности нужен отдельный путь немедленной остановки. Не считать сохранение томов Docker заменой защиты активной работы.

**5. Высокий — прерванное создание оставляет настройку, которую обычный повтор не восстанавливает. Воспроизведено с имитацией Docker.**

Источник: [agent.ts](../ctl/src/agent.ts), строки 89–94.

Итоговая метка настроек ставится при `docker create`, до копирования entrypoint. Если `docker cp` завершается ошибкой, контейнер остаётся с правильной меткой настроек. Повторная попытка находит совпадающий отпечаток, пропускает копирование и пытается запустить отсутствующий entrypoint. Имитация дала две ошибки при одной попытке копирования: сначала `simulated interrupted docker cp`, затем `entrypoint is missing`.

Исправление: рассматривать создание как транзакцию. Отслеживать инициализацию отдельно, проверять нужные файлы и при ошибке удалять только неполный контейнер, сохраняя его тома. Если это упрощает инициализацию, предпочесть неизменяемые проверенные файлы среды выполнения в небольшом производном образе. Добавить тесты с внедрением сбоев при create/copy/start и восстановлении.

**6. Высокий — у общих ресурсов и операций жизненного цикла нет межпроцессных блокировок. Статическое замечание.**

Источник: [agent.ts](../ctl/src/agent.ts), `start`; [positron-server.ts](../ctl/src/positron-server.ts), строки 30–37 и 94–110; [project.ts](../ctl/src/client/project.ts), общий кеш.

Каждый SSH-запрос выполняется отдельным процессом. Два открытия могут конфликтовать при создании/удалении контейнера, установке сервера, подготовке расширений и обновлении кеша git. Распаковка сервера использует `.tmp-<commit>-$$` в отдельных вспомогательных контейнерах; оболочка обычно имеет PID 1 в каждом из них, поэтому каталог не уникален глобально. Установка также удаляет каталог назначения до перемещения нового дерева на место. Расширения доступны для записи и общие для всех проектов пользователя на одной архитектуре, даже для разных версий Positron.

Исправление: использовать межпроцессные блокировки на уровне пользователя/проекта, архитектуры/коммита сервера и кеша расширений. Создавать временные имена вне пространства PID вспомогательного контейнера, затем атомарно публиковать проверенную установку. Никогда не удалять используемое дерево сервера при публикации. Версионировать наборы расширений по коммиту Positron и политике или дать каждому проекту собственный каталог расширений для записи. Для записи в общие тома среды выполнения использовать доверенный закреплённый вспомогательный образ, а не любой запрошенный образ окружения. Проверить одновременные открытия, прерванную установку и две версии клиента.

**7. Высокий — ограничения памяти отдельных контейнеров не обеспечивают управления ресурсами команды. Статическое замечание.**

Источник: [agent.ts](../ctl/src/agent.ts), строки 162–193; [agent.json](../ctl/examples/agent.json).

Нет ограничения допуска ни на пользователя, ни на весь хост. Пользователи могут создать много проектов, каждый получает 8 ГБ в примере или 75% памяти хоста, если ничего не указано. Четыре контейнера с ограничением 8 ГБ уже могут занять весь номинальный бюджет памяти хоста на 32 ГБ, не оставив запаса для ОС и Docker. CPU в примере сервера не ограничен; использование диска и логи Docker ничем не ограничены. Вспомогательные контейнеры не проходят через ограничения ресурсов проекта.

Исправление: резервировать ресурсы хоста, под той же блокировкой допуска ограничивать число одновременных проектов и суммарный бюджет на пользователя, задать ограничения CPU и процессов по умолчанию для проектов и вспомогательных контейнеров. Добавить мониторинг заполнения томов, оповещения о диске и inode, ротацию логов и политику хранения версий сервера и образов. Выводить число параллельных процессов и потоков R по умолчанию из выделенных ресурсов. Для небольшой команды одного сервера Docker с этими механизмами может хватить; кластер пока не нужен.

**8. Высокий — сохранность — это не резервная копия, а границу того, что сохраняется, легко понять неправильно. Статическое замечание.**

Источник: [agent.ts](../ctl/src/agent.ts), подключение томов в строках 185–188; [entrypoint.sh](../ctl/container/entrypoint.sh); [workflow.md](workflow.md).

Сохраняются только каталог проекта и выбранные каталоги Positron. Файлы в других местах домашней папки, личные библиотеки R там же, конфигурация Git и состояние known_hosts SSH могут исчезнуть при замене. В этом репозитории нет ни реализации резервного копирования и восстановления, ни руководства. Запушенный коммит Git не защищает неотслеживаемые файлы, незапушенные изменения, все результаты и состояние IDE. Потеря хоста или диска может уничтожить все эти постоянные тома сразу.

Исправление: задокументировать точные правила того, что сохраняется, и отделить одноразовое состояние окружения от долговременной работы. Делать резервные копии данных проектов зашифрованным механизмом с контролем доступа вне хоста; выбрать правила согласованности для работающих заданий. Определить целевые точку и время восстановления и действительно восстановить проект на другом хосте. Защищать расшифрованные резервные копии как чувствительные данные. Хранить воспроизводимые библиотеки R в образах, с явным порядком запроса на добавление пакетов.

**9. Высокий для долгих заданий — низкая загрузка CPU не доказывает, что работа закончена. Статическое замечание.**

Источник: [idle-watch.sh](../ctl/container/idle-watch.sh), строки 18–43.

Отключённый проект останавливается, когда средняя загрузка CPU держится ниже 5% одного ядра. Под это определение подходит и нормальное задание, ожидающее ввода-вывода от базы данных или сети, блокировки, планировщика или внешнего процесса. Выключение завершает PID 1 без сохранения промежуточного состояния приложения. И наоборот, случайная фоновая нагрузка CPU может бесконечно мешать очистке. Настройка оценки OOM повышает шанс, что будет выбран R, но не гарантирует, что во всех случаях умрёт только R.

Исправление: добавить явную аренду заданий, например `job run`/`keep-alive`, с видимым сроком действия и владельцем. Автоматически останавливать только при отсутствии и интерактивных подключений, и активных аренд. Дать выключению задокументированный период ожидания и поддержать задания с сохранением промежуточного состояния. Пока этого нет, использовать `idleMinutes: 0` для окружений с долгими заданиями без присмотра. Проверить задания, ограниченные вводом-выводом, а не только CPU, и поведение на поддерживаемой версии cgroup.

**10. Высокий — имя проекта не является уникальной идентичностью репозитория или подключения. Статическое замечание.**

Источник: [project.ts](../ctl/src/client/project.ts), строки 18–25 и 53; [layout.ts](../ctl/src/layout.ts), строки 16–34; [ssh.ts](../ctl/src/client/ssh.ts), строки 75–82; [extension.ts](../ctl/src/extension.ts), `currentProject` и `stopCurrent`.

`org-a/study.git` и `org-b/study.git` становятся одним проектом, кешем, контейнером и томами. Существующие репозитории не сверяются с запрошенным origin перед повторным использованием. Полный URL сначала работает, но боковая панель при повторном открытии сохраняет только короткое имя проекта. Открытие того же проекта на втором хосте перезаписывает тот же SSH-псевдоним; уже открытое окно потом берёт цель остановки из этого изменяемого файла и может остановить не тот хост.

Исправление: назначить постоянный ID проекта на основе явного идентификатора или канонической идентичности репозитория, отделив отображаемые имена. Хранить в метаданных проекта канонический remote, рабочую копию, владельца и хост. Проверять существующий origin перед повторным использованием. Дать SSH-псевдонимам и состоянию подключения окна идентичность с учётом хоста; остановка из окна должна использовать ту точку, которую окно действительно открыло.

**11. Высокий до использования агентов — расшифрованные данные и переадресованные учётные данные действуют долго. Статическое замечание.**

Источник: [open.ts](../ctl/src/client/open.ts), строки 85–99; [ssh.ts](../ctl/src/client/ssh.ts), строки 30–60; [admin.ts](../ctl/src/admin.ts), `removeUser`; [README](../README.md), строка 172.

Открытие с `--unlock` оставляет расшифрованную рабочую копию и состояние git-crypt в постоянном томе проекта. Следующее обычное открытие не блокирует её снова. Эти команды — не отдельные режимы безопасности. Конфигурация SSH переадресует агент пользователя на всю сессию IDE и отключает проверку ключа хоста контейнера. Код, работающий от имени аналитика, может использовать переадресованный агент, пока он доступен, хотя просто извлечь закрытый ключ не может. Удаление пользователя лишь отменяет будущую авторизацию на шлюзе; оно не завершает установленные сессии и не стирает ключ, уже находящийся в работающем контейнере.

Исправление: разделить тома людей, агентов и CI на реальных данных. Давать агентам ограниченные ключи репозитория, без переадресованного агента человека и без расшифрованного тома. Показывать фактическое состояние расшифровки, определить явное поведение блокировки и хранения ключей и никогда не считать, что остановка контейнера снова шифрует файлы. Закреплять ключи хостов контейнеров через аутентифицированное управляющее соединение или использовать сертификаты хостов SSH. Отключение пользователя должно прекращать доступ и сессии согласно политике; данные сохранять и архивировать отдельно. Рассмотреть ключи git-crypt для каждого проекта и политику разрешённых хостов для расшифровки.

**12. Средний–высокий — сеть контейнеров и доверие к образам шире, чем заявленная изоляция проектов. Статическое замечание.**

Источник: [agent.ts](../ctl/src/agent.ts), `createArgs`; [agent-config.ts](../ctl/src/agent-config.ts), `DEFAULT_ALLOWED_IMAGES`; [positron-server.ts](../ctl/src/positron-server.ts), `helperArgs`.

Контейнеры проектов используют стандартный мост Docker и неограниченный исходящий трафик. Публикация только на loopback ограничивает доступ к портам хоста, но не изолирует соседей по мосту. Другие сервисы, доступные по IP контейнеров, тоже могут иметь значение. Разрешённый префикс образов доверяет каждому образу организации, включая код, выполняемый от root во вспомогательных контейнерах, которые пишут общие файлы сервера. Это существенные допущения о доверии. [Документация Docker по мосту](https://docs.docker.com/engine/network/drivers/bridge/) описывает связь между соседями и подключение к сети по умолчанию.

Исправление: явно указать, что в рабочих областях людей выполняется доверенный код команды; не представлять это как защищённую песочницу для произвольного кода. Где нужно, использовать отдельные сети для проектов и явную политику исходящего трафика. Разрешать только точные одобренные репозитории/дайджесты, закрепить вспомогательные образы и защитить права публикации. Для пакетных задач и агентов запускать образ анализа без root, со сброшенными capabilities, no-new-privileges, ограниченными ресурсами и, где практично, файловой системой только для чтения. Усиление защиты для SSH проверять отдельно, потому что sshd нужны дополнительные привилегии. Изолировать недоверенные раннеры и раннеры с чувствительными данными на отдельных хостах/ВМ, когда этого требует их граница доверия.

**13. Средний — обработка ошибок и выбор локального хоста могут вводить пользователей в заблуждение. Статические замечания.**

Источник: [open.ts](../ctl/src/client/open.ts), строки 42–58 и 85–101; [transport.ts](../ctl/src/client/transport.ts), `SshTransport.call`; [engine.ts](../ctl/src/client/engine.ts), `Engine`; [exec.ts](../ctl/src/exec.ts), `run`.

Ошибки клонирования/синхронизации и запрошенной расшифровки дают только предупреждение; открытие всё равно сообщает об успехе. У нескольких операций есть только таймауты SSH-подключения, без срока после подключения. Вывод дочерних процессов накапливается без ограничений. Вызовы Docker для Colima/Desktop/системы используют текущий контекст и окружение Docker, поэтому хост с меткой local может на самом деле обращаться к отдельно настроенному удалённому демону. Маркер владения движком — простой флаг существования, а не запись жизненного цикла с учётом идентичности. Автоматический переход с сервера на локальную машину может также перенести расшифрованную работу на ноутбук без явной политики размещения данных.

Исправление: различать состояния «готово», «работает, но устарело» и «ошибка»; первое клонирование или запрошенная расшифровка должны явно завершаться ошибкой. Добавить общие сроки, отмену, ограниченные логи и очистку процессов. Привязать каждый движок к явной проверенной точке/контексту Docker и отслеживать владение по идентичности движка. Разрешать переход только на хосты, одобренные политикой. Учесть при запуске CLI на Windows обёртки `.cmd` и проверить, что собственные SSH-ключи работают через ProxyJump, а не только в прямом управляющем соединении.

**14. Пробел с высокой уверенностью — тесты проверяют вспомогательные функции, а не ключевые обещания платформы.**

Источник: [units.test.ts](../ctl/test/units.test.ts), [lint.yml](../.github/workflows/lint.yml), [env-image.yml](../.github/workflows/env-image.yml).

14 тестов полезны, но в основном покрывают валидаторы, форматирование строк, конфигурацию и создание tar. Они не проверяют фактический жизненный цикл Agent, контроль владельца в SSH, восстановление после неудачной настройки, обновления при активных заданиях, поведение clone/sync, выключение при простое, восстановление из резервной копии и интеграцию с Windows/Positron. Workflow образа публикует без этапа дымовой проверки анализа/отчёта; на PR образы не собираются. Отдельные workflow для lint и публикации не гарантируют, что публикация ждёт успешной проверки.

Исправление: превратить воспроизведённые сбои в регрессионные тесты. Добавить одноразовые интеграционные тесты на Linux с двумя пользователями и несколькими проектами, включая тесты отказа в доступе, одновременные запуски, прерванное создание, сохранность томов, несоответствие ветки и окружения и отключение пользователя. Перед продвижением образа рендерить показательный документ Quarto и загружать нужные нативные пакеты R. Собирать на PR без публикации, затем публиковать проверенные дайджесты из доверенных коммитов. Закрепить сторонние Actions на проверенных SHA коммитов и добавить ревью уязвимостей зависимостей и образов, сведения о происхождении и явный процесс выпуска и отката.

**15. Средний — проверка R-окружения — хорошее начало, но правила воспроизводимости неполны.**

Источник: [Dockerfile](../env/Dockerfile), строки 14–53; [renv.lock](../env/renv.lock); [snapshot-date.sh](../env/snapshot-date.sh).

R_VERSION сейчас соответствует lock-файлу, и в проверенном образе совпали все зафиксированные пакеты. Однако проверка версий при сборке явно исключает рекомендуемые пакеты, не сверяет работающую версию R с lock-файлом и проверяет только строки версий. Lock-файл удаляется из образа, а дополнительно установленные пакеты не записываются в манифест образа. Apt и базовый образ не закреплены по содержимому. Вспомогательный скрипт снимка допускает неудачные запросы и поэтому даёт дату-кандидат, а не доказательство того, что для каждой зависимости есть бинарный пакет для каждой архитектуры.

Исправление: сохранять в образе lock-файл и машиночитаемый манифест; проверять в CI версии R, Quarto и пакетов. Либо согласовать рекомендуемые пакеты, либо задокументировать и проверять явные исключения. Закрепить дайджест базы и сохранять опубликованные дайджесты образов проектов; если нужна точность пересборки из исходников, сохранять или снимать также источники ОС и пакетов. Добавить тесты нативных пакетов и отчётов на каждой поддерживаемой архитектуре. Установить задокументированную политику для пакетов отдельных проектов, в идеале общая база плюс неизменяемый образ зависимостей для каждого проекта. Записывать вместе с результатами анализа версии данных, настройки ГСЧ, локаль, часовой пояс и нужные настройки вычислений и потоков.

**16. Средний — документация по развёртыванию и заявленные поддерживаемые платформы противоречат друг другу.**

Источник: [README](../README.md), [workflow.md](workflow.md), [next-steps.md](next-steps.md), [package.json](../ctl/package.json), [install.sh](../ctl/server/install.sh), [setup-wsl.ps1](../ctl/windows/setup-wsl.ps1).

Инструкция для аналитиков помечена как устаревшая и описывает локальные папки/Dev Containers, тогда как текущая работа хранится в томах Docker через собственный удалённый процесс. Документ next-steps перечисляет уже реализованные боковую панель и диагностику как будущую работу. Инструкции для сервера допускают Node 20, а пакет требует Node 22.18, и сборки нацелены на Node 22. Значения простоя по умолчанию в тексте и настройках колеблются от 60 до 120 минут. Несколько комментариев в образе всё ещё ссылаются на удалённые пути. Начальная настройка Windows жёстко задаёт x86_64 и требует реального сквозного пилота, включая сеть и поведение агента учётных данных.

Исправление: опубликовать единую матрицу поддержки для ОС/CPU клиента, архитектуры образа, версии Positron, Node, Docker и cgroups. Согласовать проверки в коде и документацию. Написать короткую инструкцию для аналитиков: подключение, открытие, изменение пакетов, сохранение и push, состояние расшифровки данных, сохранность заданий, переход между хостами, восстановление и диагностика для поддержки. Установку, обновления, резервное копирование, отключение пользователей и процедуры при инцидентах держать в отдельном руководстве оператора. Явно отмечать непроверенные сочетания.

**Рекомендуемая цель и порядок работ**

При текущем масштабе команды сохраните один управляемый Linux-хост с Docker и существующие CLI и расширение. Сделайте окружение независимым от редактора и дайте каждой роли выполнения свою политику доступа:

| Роль | Рабочая область | Данные | Учётные данные | Политика выполнения |
| --- | --- | --- | --- | --- |
| Аналитик | Долговременный том проекта с резервными копиями | Явно разрешённые; состояние расшифровки видно | Узкий доступ человека | Интерактивно, с квотами, с учётом заданий |
| Агент, пишущий код | Одноразовый клон и синтетические тестовые данные | Без расшифрованных данных и томов людей | Ограниченный доступ к репозиторию | Ограниченные сеть и среда выполнения |
| Задание отчёта на реальных данных | Свежая выгрузка согласованного коммита | Разрешённый снимок только для чтения | Краткосрочные минимальные учётные данные | Одноразовый раннер, контролируемая публикация результатов |

Используйте один и тот же неизменяемый артефакт зависимостей R для всех этих ролей; им нужны разные подключения, сетевые права, учётные данные и entrypoint. В текущем образе нет финального `USER analyst`, поэтому прямой пакетный `docker run` должен явно выбирать пользователя без root или использовать отдельный пакетный образ.

1. Закрыть уязвимость с переадресацией на шлюзе; определить модель угроз для CI и данных; прекратить автоматические разрушительные обновления; исправить частичное создание; ввести идентичность проектов и межпроцессные блокировки.
2. Закрепить дайджесты образов и привязать выбор окружения к фактической рабочей копии. Добавить дымовые тесты выпуска и интеграционные тесты жизненного цикла и безопасности.
3. Добавить суммарное управление ресурсами, резервное копирование с учениями по восстановлению, явную аренду заданий и надёжное отключение пользователей. Исправить документацию для аналитиков и оператора.
4. Провести пилот с двумя людьми и одним показательным анализом на настоящем сервере. Проверить разрыв и восстановление соединения, одновременные открытия, обновление и откат пакетов, расшифровку данных, завершение заданий и восстановление. Затем проверить каждую поддерживаемую клиентскую платформу.
5. Добавлять выполнение агентов и CI на реальных данных только после того, как реализованы отдельные политики доступа и контроль согласований и результатов.

Главный критерий успеха: два аналитика могут заново открыть одно и то же сочетание кода, данных и окружения, закончить долгий анализ несмотря на разрыв соединения, восстановить работу после отказа хоста и не могут пересечь задуманные границы доступа. Прохождение lint и создание образа контейнера необходимы, но этих результатов не обеспечивают.
