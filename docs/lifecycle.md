# Lifecycle invariants and recovery

This is the contract for control-plane changes. The CLI and extension share the same application layer (`ctl/src/agent.ts`). Capacity policy is in `capacity.ts`, read-only deletion inspection in `removal-inspection.ts`, image ingestion in `image-store.ts`, and kernel locks in `lock.ts`.

## Environment identity

A project pins an immutable environment image. Its `renv.lock` adds the desired R package versions and source provenance. Every ordinary R startup, including Rscript and Quarto, verifies installed versions and `Remote*` provenance. Missing or mismatched packages trigger restoration under a project environment lock. A failed restore exits before analysis and leaves no success marker. Restarting R retries.

Use `renv::install()` for intentional changes, then run `fnkc-projects snapshot` in the terminal **before starting another R session**. Snapshot deliberately observes installed changes instead of restoring over them. It requires a successful restore of the current lockfile, compares full source records (including `RemoteSha`), writes and validates a candidate, and atomically replaces `renv.lock`. Review and commit it. Stopping a container never snapshots or rewrites dependencies. Explicit startup bypasses such as `R --vanilla` remain expert tools, outside this guarantee; containers execute trusted team code.

Runtime state lives under `renv/.fnkc-*`, excluded locally from Git. A kernel lock serializes restore and snapshot. Manual package installation should not run concurrently with analysis, restore, or snapshot. Ordinary Git operations do not participate in this lock; concurrent lockfile edits are detected before committing a snapshot or successful restore.

## Project lifecycle

- **Initializing:** `.fnkc-init/repo` contains an unexposed clone on the project volume. Interrupted cloning can be retried. Once ready, a request record pins its repository/revision and top-level entries move atomically into place. Retry preserves entries already promoted and refuses conflicting destinations. `.fnkc-init-done` is disposable completed staging.
- **Ready/stopped:** the canonical container name is `fnkc-<user>-<project>`. Labels identify its user and project. A project literally named `study-previous` is valid and visible.
- **Replacing:** the old stopped container is renamed to `fnkc.recovery.<user>.<project>`, outside the public namespace. Its immutable ownership labels remain attached. A missing new container causes rollback on retry; an unstarted replacement is discarded without volumes and the old one restored; a running replacement must pass readiness before the old one is removed.
- **Legacy recovery:** `<canonical>-previous` is recognized only when its ownership labels identify the original project. A real suffix-named project is never treated as recovery. Legacy `.fnkc-initializing` clones still require operator inspection because their previous implementation did not record sufficient resumable state.

An existing checkout's manifest/revision takes precedence over remote HEAD, including a staged initialization ready for promotion. Clone commands have a 30-minute deadline. A timeout may leave resumable staging, never an instruction to overwrite user work.

## Lock ordering and availability

Project operations acquire `project-<user>-<project>`. Starts hold the host admission lock only while checking running resource budgets and starting the container. Slow pulls, extension setup, stops, cloning, and backups do not hold admission. Image ingestion is serialized by `image-upload`; loading, pulling and image removal share `image-store`. Image operations never acquire project locks. On the client, Open holds a lock per project (two projects open at the same time; a second Open of the same project waits up to two minutes), and downloading an image holds a lock per digest, so two Opens that need the same image download it once. Offboarding (`admin remove-user`) first removes the key under the host lock, then stops each running project under its project lock; a start in progress checks the key again under the host lock before admission, so it cannot start a container for a revoked user. Backups use the same project lock as starts, stops and removal; restoring into unrelated names uses a volume lock.

POSIX uses Python 3 `fcntl.flock`; Windows clients use PowerShell named mutexes. Kernel ownership ends on process termination. Persistent `*.kernel` files must **never be deleted** as a recovery action: deleting a locked inode creates a second lock domain. A lost lock helper terminates its owner rather than continuing a mutation without exclusion. Direct Docker operations by administrators bypass this coordination.

## Deletion

Preview fingerprints include deterministic tar content of every durable project volume (including Git objects/refs, untracked and ignored files) and streamed hashes of the stopped container’s changed filesystem paths; the immutable image ID identifies unchanged base files. Deletion recomputes them under the project lock and refuses differences. A failure to read or fingerprint storage prevents deletion. Fingerprinting can take time and read substantial data; deletion is not a constant-time metadata operation.

The report's remote branches are the checkout's last fetched knowledge, not a live guarantee of server retention. Filesystem timestamps alone are normalized in volume fingerprints. Administrators must not mutate or mount a project's storage during preview/deletion. This is concurrency protection for managed operations, not a filesystem snapshot or a backup. Keep independent backups for recovery from intentional deletion.

## Upload and storage bounds

Only one upload stages at a time per host. Additional callers wait up to an hour for their turn and say so ("Waiting for another image upload to this host to finish"); the client keeps the quiet SSH connection alive meanwhile. Reading data or EOF has a 60-second idle deadline and a four-hour overall deadline. Failed uploads clean up staging; the next ingestion removes remnants left by killed upload processes. Digests and architecture are verified before loading.

Defaults in agent configuration:

| Setting | Default | Meaning |
| --- | --- | --- |
| `imageReserve` | `2g` | Free staging space retained beyond declared compressed blobs |
| `maxUnpackedImage` | `64g` | Maximum decompressed layer-stream bytes per uploaded image |
| `maxImageStorage` | `128g` | Conservative sum of Docker image sizes plus incoming unpacked bytes |

The wire format also caps manifests at 4 MiB and compressed images at 32 GiB. Decompression is bounded before Docker extraction. Logical image accounting can double-count shared layers; it intentionally errs toward refusing an upload. These limits are admission policy, not a filesystem quota: unrelated Docker workloads, filesystem overhead and sparse archives require host disk monitoring and a separate Docker data-root capacity/quota policy. Registry pulls are trusted Docker operations and should be provisioned with the same host disk limits.

Digest verification proves content identity. For enrolled server agents (`keysDir` configured), every start also requires a GitHub Artifact Attestation for the runnable image, signed by the configured repository's `.github/workflows/positron.yml` on `refs/heads/main`. Clients download bundles from the GitHub API (inline, or linked and snappy-compressed; with `GH_TOKEN`, `GITHUB_TOKEN` or the `gh` login when there is one, which raises GitHub's limit from 60 requests an hour per address to 5000 per account, sent to `api.github.com` only) and the image's top manifest from the registry, and cache both by digest. The server checks that the manifest's sha256 is the pinned digest and runs `gh attestation verify` on that file with the installed Sigstore trusted root: offline, without the registry or GitHub credentials. It refuses missing or invalid proofs before creating or replacing a container; a running or unchanged existing container needs no proof (connect checks its verified-image mark). Digests that passed are remembered in `verifiedDir` under the signer policy; a policy change verifies again. The trusted root is refreshed weekly by a systemd timer that keeps the previous file when a download fails. `positron.yml` verifies every image this way after attesting it under `staging-<tag>` and before moving the `positron-*` tag to it (`test:provenance`, gh in a container without network; it reuses a published image only when its recipe label `positron.recipe` matches and its attestation verifies, and `positron-promote.yml` moves a tag back to an earlier verified digest), and `ctl-checks.yml` does the same for the template pin's Positron image before every release and pin change (`ctl/test/provenance-pin.sh`), so a change that breaks real verification does not ship. Local-only agents default to no provenance requirement. Existing Positron layers need a fresh **Build Environment** dispatch before they can start under the new policy; it creates a new image digest and attestation. Existing monolithic images with Positron built in must be replaced by a newly attested environment/server image and a reviewed project pin.

## Upgrade and validation

Upgrades go **server first**. A server accepts clients of the previous release: new request fields are optional and new reply fields are ignored by older clients. The server reports its packaged software version, the range of protocol versions it serves (`minProtocol` to `protocol`), and capabilities; clients reject mutations against servers whose range does not include their protocol or that miss the capabilities they require, and build numbers need not match. A change older clients cannot ignore raises the protocol version while the server keeps serving the previous one, so the server can still be upgraded first. Failures carry a `code` (`ctl/src/errors.ts`) that clients act on, so rewording a server message changes no client's behaviour. Each release publishes `fnkc-projects-compat.json` (`fnkc-ctl --version --json`: protocol and required capabilities); the extension offers a release only when every configured server that answers has them, and postpones the automatic offer while a server cannot be asked. Install Python 3 on macOS/Linux clients and the Linux service host.

A running container is never replaced. When a start would set it up differently (new pin, fnkc-ctl assets, key, limits), the host answers with the running container and `updatePending: true`, and the client connects to it as it is and says that the update waits for an explicit stop. The extension's Projects panel then shows that container as "running · update pending" (kept per host and container across reloads) until a listing shows it stopped or gone, or an Open of it comes back without `updatePending`. This requires the container to serve the client's Positron build; otherwise the start is refused with a request to stop and reopen.

Releases: `install.sh` stages each version whole in `/opt/fnkc-ctl/releases/<version>-<checksum>` (all program files and a `MANIFEST` of their checksums), checks it, records the replaced release as `previous-release`, and then switches the single `current` link; the program paths under `/opt/fnkc-ctl` are fixed links through it, so every file changes at once, under an installer lock. Rollback: `sudo /opt/fnkc-ctl/install.sh --rollback` swaps `current` and `previous-release` after a confirmation (a second rollback rolls forward), and refuses a previous release whose files do not all match its `MANIFEST`. `fnkc-ctl admin status` shows both release IDs and any file that does not match. Clients that already updated to a release requiring the newer server refuse the rolled-back one until they install the matching older `.vsix` (with `fnkcProjects.checkForUpdates` off). Release notes say whether the server bundle changed since the previous release (its files compared with each build's version number masked).

Release publication depends on `ctl-checks.yml`: lint/typecheck/unit tests (the same `./lint.sh` the pre-commit hook runs, including the secret scan), `npm audit` of the build tools, real provenance verification of the template pin's published Positron image, real SSH access and revocation, encrypted backup/restore, clone interruption recovery, noninteractive R restoration and source provenance, and the complete local/server opening workflow. Fixtures use synthetic data and disposable containers. Unit regressions also kill lock owners, stall uploads, exceed decompression budgets, change content without changing Git status, and stop projects during unrelated pulls. Run `./lint.sh` locally; integration commands are listed in that workflow.

## Release history and one-time migrations

These applied once, when moving from an older release; the current rule is the one above (server first, any time).

- **0.3:** the Positron server is part of the image (neither host nor client downloads it), and projects, containers and volumes are named after the Gitea repository. Server and clients were updated together. Containers and volumes made by 0.2 (with a hash in the name) are not used: push the work, stop them and delete them after checking.
- **0.4:** protocol and package rules changed; server and clients were updated together, with old processes ended. macOS/Linux need Python 3. Dependencies are snapshotted explicitly (`fnkc-projects snapshot`); stopping does not change `renv.lock`. Old directory locks are no longer used; leave them alone until old processes have exited. No existing project volumes are renamed. Recovery containers migrate only after their labels prove ownership. Existing R libraries remain on their current volumes.
