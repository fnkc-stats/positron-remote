# Руководство оператора

Серверу нужны Linux/systemd, Docker Engine, Node 22.18+, Python 3, GitHub CLI и права root для установки и подключения пользователей. Доступ к демону Docker и право публиковать образы считайте правами администратора. Контейнеры аналитиков предназначены для доверенного кода команды. Автоматическую обработку чувствительных данных выполняйте на отдельном хосте.

## Установка и настройка

Соберите `npm --prefix ctl run server-bundle`, перенесите полученный `ctl/dist/fnkc-ctl-server.tar.gz`, распакуйте и выполните `sudo ./fnkc-ctl-server/install.sh`. Установщик обновляет программу, создаёт служебную учётную запись и общий каталог блокировок, заменяет старый префикс образов по умолчанию точным репозиторием, заново создаёт управляемые строки authorized_keys, записывает фрагмент конфигурации sshd, запрещающий переадресацию, проверяет его и перезагружает sshd. Нужно стандартное подключение `/etc/ssh/sshd_config.d/*.conf`. Старые SSH-сессии установщик не завершает, и окно обслуживания для обновления не нужно (см. [Обновление и откат](#обновление-и-откат)). После каждой правки `agent.json` выполните `fnkc-ctl admin check-config`: команда (root не нужен) печатает действующие настройки с подставленными значениями по умолчанию и предупреждает о неизвестных ключах — опечатка вроде `"idleMinute"` иначе молча оставляет значение по умолчанию. Синтаксическую ошибку агент находит только при следующем запросе, то есть сразу у всех пользователей; установщик выполняет эту проверку в конце.

Настройте `/etc/fnkc-ctl/agent.json` по образцу `ctl/examples/agent.json`:

- `allowedImages`: точные доверенные репозитории; каждый запрос должен содержать дайджест SHA-256. Защитите право записи в эти репозитории.
- `limits`: положительные ограничения памяти и CPU плюс ограничение числа процессов. Ограничение 8 ГБ на проект — не резервирование 8 ГБ на уровне ОС; допуск консервативно суммирует заданные ограничения.
- `maxProjectsPerUser`, `maxMemoryPerUser`, `reserveMemory`: бюджеты допуска. `maxProjectsPerUser: 0` временно запрещает запуск проектов (например, на время обслуживания); работающие проекты продолжают работать. При превышении квоты пользователь видит список своих работающих проектов. Работающие контейнеры без ограничения памяти считаются занимающими ресурсы хоста, поэтому прежде чем допускать проекты анализа, уберите посторонние нагрузки без ограничений или ограничьте их.
- `lockDir`: `/var/lib/fnkc-ctl/locks`, общий для запросов службы, администрирования от root и инструментов резервного копирования. Никогда не используйте разные каталоги блокировок с одним и тем же демоном Docker.
- `idleMinutes`: 120 (так в примере конфигурации). Контейнер без окна и без нагрузки останавливается через 2 часа; считающий без окна — через 3 дня после закрытия последнего окна, и за 2 дня до этого Positron пользователя предлагает продлить (подробно: [Правила](policies.md)). `0` — никогда не останавливать. `agent.json`, созданный более ранней установкой, не меняется: поставьте 120 сами. Научите аналитиков запускать долгие задания через `fnkc-projects run`.
- `pullImages`: по умолчанию `false`. Хостам не нужен доступ к реестру: недостающий образ окружения присылает клиент (см. [Образы окружения](#образы-окружения)). Установите `true` там, где реестр доступен: тогда хост сначала пробует `docker pull`, это быстрее; если скачать не удалось, образ всё равно пришлёт клиент.
- `cranMirror`: зеркало CRAN для пакетов, которых нет в образе (`renv::install()` и восстановление `renv.lock` в контейнерах), по умолчанию `https://mirror.truenetwork.ru/CRAN/`. Только https, адрес оканчивается на `/`. Изменение применяется при пересоздании контейнера (остановите проект и откройте снова).
- `extraHosts`: имена, которые известны только DNS VPN этого компьютера, например `{"git-srv.example.ru": "10.0.0.5"}`; передаются контейнерам проектов как `--add-host`. Нужно для хоста `local` на Mac с раздельным DNS VPN: DNS Docker Desktop его не использует, и клонирование из Gitea завершается ошибкой «Could not resolve hostname». Записи применяются при создании контейнера.
- `imageStagingDir`: куда принимаются и где проверяются загруженные образы перед `docker load` (по умолчанию внутри `~/.cache/fnkc-ctl/images` служебной учётной записи). Нужно свободное место для самого большого образа, для `r-env` около 1 ГБ в сжатом виде; после каждой загрузки каталог очищается.
- Сервер Positron — отдельный слой поверх R-окружения (`~/.positron-server/bin/<commit>`, метки `positron.version`, `positron.commit` и `r-env.base`); хост и клиенты его не скачивают. Проект закрепляет окружение, а хост запускает образ с сервером Positron клиента, только если тот собран на закреплённом окружении (`r-env.base`) и для этой сборки Positron; иначе отклоняет до создания контейнера. Закреплённое окружение на хосте не нужно. Настройки `serverUrlTemplate`, `quality` и `serverArchiveDir` больше не используются, их можно удалить из `agent.json`; том `fnkc-server-<arch>` версии 0.2 можно удалить, когда не останется контейнеров 0.2.

Контейнеры проектов запускаются без лишних привилегий Linux: оставлены только `AUDIT_WRITE CHOWN DAC_OVERRIDE FOWNER KILL NET_BIND_SERVICE SETGID SETUID SYS_CHROOT` (sshd и скрипт запуска) и `no-new-privileges`. После обновления fnkc-ctl остановленные контейнеры пересоздаются при следующем открытии (тома сохраняются).

Проверьте действующие настройки командой `sudo sshd -T -C user=fnkc,host=localhost,addr=127.0.0.1`. `disableforwarding` должен быть `yes`. Пользователи добавляются командой `sudo fnkc-ctl admin add-user anna anna.pub`. Передайте проверенные отпечатки ключей хостов шлюза и Gitea по доверенному каналу. Пока эти ключи хостов не признаны доверенными, SSH-операции клиента завершаются ошибкой.

Размещайте хост на файловой системе, где отслеживаются свободное место и inode. Если рост результатов нужно ограничить, настройте квоты на проекты или файловую систему. Ротация логов в контейнерах проектов настроена, но именованные тома, образы окружения, каталог приёма образов и сохранённые среды выполнения IDE всё равно требуют управления местом. Не выполняйте без разбора `docker system prune --volumes`: так можно уничтожить работу пользователей с остановленными проектами. Удаляйте только проверенные ресурсы, у которых есть резервная копия и на которые ничего не ссылается.

## Образы окружения

Проекты закрепляют образы по дайджесту. Всё, что им нужно, включая R-пакеты, есть в образе ([r-packages.md](r-packages.md)), поэтому работающему контейнеру не нужен репозиторий пакетов, а хосту — реестр:

1. Открытие просит хост запустить проект. Если закреплённого образа на хосте нет (и `pullImages` выключен или скачать не удалось), хост отвечает, какой образ нужен и какая у хоста архитектура.
2. Клиент скачивает образ по дайджесту на компьютере пользователя через HTTP API реестра (публичные образы, анонимный токен; Docker на клиенте не нужен). Для мультиархитектурного образа скачивается только архитектура хоста. Блобы проверяются и хранятся в кеше клиента (`images/` в каталоге кеша), поэтому для следующего хоста или повторной попытки они не скачиваются заново.
3. Клиент передаёт манифесты и блобы потоком через шлюз (`agent install-image <image>`). Хост в `imageStagingDir`, не удерживая блокировку хоста, сверяет манифест с закреплённым дайджестом, каждый блоб — с манифестом, а архитектуру — с архитектурой хоста. Только после этого он под отдельной блокировкой образов собирает из проверенных файлов архив для `docker load` и помечает образ тегом `<repository>:sha256-<digest>`. Реестры сохраняют дайджест образа, а `docker load` — нет, поэтому fnkc-ctl, скрипт резервного копирования и рендерер проверенных отчётов используют этот тег для загруженного образа и ссылку на реестр — для скачанного.
4. Открытие повторяет попытку и запускает контейнер. Образ передаётся один раз для каждой пары хоста и дайджеста.

**Доверие.** Дайджест подтверждает содержимое образа, а GitHub Artifact Attestation подтверждает, что runnable Positron-слой построен разрешённым workflow из `main`. Workflow `positron.yml` публикует attestation для конечного multi-architecture digest. Клиент получает bundles по GitHub API и манифест образа из реестра (один раз на дайджест: они кешируются; если на компьютере есть вход `gh` или `GH_TOKEN`, запрос идёт с ним: без входа GitHub разрешает 60 запросов в час с одного адреса, и при общем адресе офиса лимит может кончиться — тогда открытие называет время сброса); сервер проверяет их офлайн с установленным GitHub Sigstore trust root, включая digest, repo, workflow и source branch, до создания контейнера, и запоминает проверенный дайджест (`verifiedDir`). Если GitHub недоступен, уже проверенные на сервере образы и работающие проекты открываются как обычно. Подключённый пользователь может загрузить собственный образ в Docker, но не сможет запустить его без действительного attestation от разрешённого workflow. При `docker pull` и ручном `docker load` импортируйте именно attested digest. Старые образы без provenance отклоняются: для миграции запустите **FNKC Projects: Build Environment** для используемых пар окружение/Positron, дождитесь новой публикации и откройте снова. Новая сборка получает новый digest. Устанавливайте GitHub CLI на сервер; сетевой доступ нужен установщику и еженедельному таймеру `fnkc-ctl-trust-root.timer` для обновления trust root (без сети остаётся прежний файл; вручную: `/opt/fnkc-ctl/refresh-trust-root.sh`) и клиенту для получения bundle, но проверка на сервере выполняется офлайн.

**Какие образы где.** Панель **Environment Images** в расширении (или `fnkc-ctl images`) показывает:

- опубликованные R-окружения по сериям, новые сверху, по одной строке на образ; под каждым — слои с сервером Positron, собранные для него (раскройте строку), и пометка, если для вашей версии Positron слоя ещё нет. «newest» — самое новое окружение серии; серым — окружения, которые не самые новые, не закреплены шаблоном и не используются контейнерами на доступных хостах, и неиспользуемые слои;
- закрепляет ли шаблон Gitea каждой серии (`template-r-<серия>`, настройка `templateRepository`) самое новое окружение. Шаблоны читаются так же, как `container.json` проекта при открытии; если Gitea недоступна, показывается закрепление, прочитанное в прошлый раз;
- образы на каждом хосте (`agent images`): размер на диске, число контейнеров проектов всех пользователей, сделанных из образа, и сколько из них запущено. Имена чужих проектов не передаются, только числа. Хост со старым fnkc-ctl отвечает, что не умеет перечислять образы; открытие проектов на нём работает как прежде.

**Очистка реестра.** `fnkc-ctl images --cleanup` показывает, что можно удалить из реестра, и ничего не удаляет; с `--delete` удаляет (нужен `gh` с правом `delete:packages`: `gh auth refresh -s read:packages,delete:packages`). Под удаление попадают:

- окружения, которые не самые новые в своей серии, не закреплены шаблоном, не используются контейнерами на хостах и созданы не меньше `--older-than` дней назад (по умолчанию 30), вместе со всеми слоями Positron на них;
- слои для версии Positron, которую команда уже не использует (не та, что в `env/positron.args`), старше 60 дней, если их не использует ни один контейнер;
- образы со встроенным сервером (до разделения), если они не используются;
- слои, окружения которых уже нет в реестре.

Каждый образ удаляется вместе с тегами отдельных архитектур. Команда видит только шаблоны и хосты, а не закрепления всех проектов в Gitea: передайте их через `--keep <файл>` (любой текст с дайджестами `sha256:…`, например вывод поиска по `container.json` всех репозиториев). Если какой-то хост, шаблон или реестр не прочитан, `--delete` отказывается. Удалённый слой Positron собирается снова через Build Environment; открытие, которое помнило удалённый слой, само ищет его заново.

Неиспользуемый образ на сервере удаляет администратор: кнопка в строке копирует команду (`sudo docker image rm <id>`); Docker откажет, если образ использует какой-либо контейнер. Образ на этом компьютере удаляется кнопкой в панели (с подтверждением, только если ни один контейнер его не использует).

## Обновление и откат

**Правило: сначала сервер, в любое время, потом клиенты.** Новый сервер работает с клиентами предыдущего выпуска; работающие проекты продолжают работать, а их пересоздание под новую версию ждёт явной остановки (`updatePending`). Нужно ли ставить новый `fnkc-ctl-server.tar.gz`, сказано в заметках выпуска: «Server bundle … changed since …: yes/no».

Обновление — повторный запуск установщика из нового архива (`sudo ./fnkc-ctl-server/install.sh`). Доступ к GitHub для этого не нужен: если загрузить свежий корень доверия Sigstore не удалось, установщик предупреждает и оставляет установленный файл. При первой установке на сервер без доступа к GitHub сделайте файл на компьютере с `gh` (`gh attestation trusted-root > trusted-root.jsonl`), перенесите его и выполните `sudo FNKC_TRUSTED_ROOT=trusted-root.jsonl ./fnkc-ctl-server/install.sh`; так же его можно заменить позже: `sudo /opt/fnkc-ctl/refresh-trust-root.sh --from trusted-root.jsonl`. Возраст корня виден пользователям в **Check Setup** (старше 30 дней — строка сервера красная) и в отказе проверки provenance; состояние таймера: `systemctl status fnkc-ctl-trust-root.service`.

Установщик сохраняет заменённую версию в `/opt/fnkc-ctl/previous`. Откат: `sudo /opt/fnkc-ctl/install.sh --rollback` показывает установленную и прежнюю версии и спрашивает подтверждение (`--yes` — без вопроса, для скриптов); повторный откат возвращает новую версию. Настройки, пользователи, образы и работающие проекты не меняются. Если установщик меняет `agent.json` (новые обязательные настройки), он сначала пишет новую версию рядом, проверяет её от имени `fnkc` и только потом подменяет файл; прежняя версия остаётся в `/etc/fnkc-ctl/agent.json.prev`. Откат программы этот файл не трогает: при необходимости верните прежние настройки сами (`cp -p /etc/fnkc-ctl/agent.json.prev /etc/fnkc-ctl/agent.json`, затем `fnkc-ctl admin check-config`). Пользователи, чьё расширение уже обновилось и требует нового сервера, увидят это в Check Setup: им нужно поставить предыдущий `.vsix` из [Releases](https://github.com/fnkc-stats/positron-remote/releases) и выключить `fnkcProjects.checkForUpdates` до следующего обновления сервера.

## Резервные копии и восстановление сервера

**Резервных копий томов команда не делает.** Копия работы — Gitea: всё, что не запушено, может пропасть вместе с сервером. Пушьте работу регулярно; при удалении проекта fnkc-ctl показывает, что не запушено.

Скрипт `/opt/fnkc-ctl/volume-backup.sh` остаётся для разовых архивов в зашифрованный репозиторий restic, например тома отключённого пользователя с незапушенной работой перед удалением. Он отказывается копировать том работающего контейнера и берёт ту же блокировку проекта, что и агент:

```bash
/opt/fnkc-ctl/volume-backup.sh backup fnkc-anna-<project>-project <approved-image@sha256:...>
/opt/fnkc-ctl/volume-backup.sh restore <snapshot-id> /fnkc-anna-<project>-project.tar fnkc-restore-<unique-id> <approved-image@sha256:...>
```

Путь к архиву показывает `restic ls <snapshot-id>`; целевой том не должен существовать. Копирование успешно, только если команда вернула ноль.

**Потеря сервера.** На новом сервере: установите fnkc-ctl (см. выше), перенесите `/etc/fnkc-ctl/agent.json` (если его копии нет — настройте заново) и добавьте пользователей снова (`fnkc-ctl admin add-user`, их ключи — те же, что в Gitea). Раздайте пользователям новый адрес и отпечаток ключа хоста. Проекты открываются заново из Gitea; образы окружений приходят с первым открытием.

## Журнал запросов

Все пользователи входят под одной учётной записью `fnkc`, а сообщения агента уходят клиенту. Поэтому каждый запрос агента и каждая команда `admin add-user`/`remove-user` оставляют одну строку в системном журнале с тегом `fnkc-ctl` (через `logger`; успешные с приоритетом info, ошибки warning). Потерянная строка запрос не останавливает, поэтому установщик в конце отправляет от имени `fnkc` пробную строку `command=install-probe` и предупреждает, если `logger` нет или строка не дошла до журнала:

```
journalctl -t fnkc-ctl --since today
journalctl -t fnkc-ctl -p warning          # только ошибки
journalctl -t fnkc-ctl | grep 'user=anna'
```

Строка состоит из полей `ключ=значение`; значения с пробелами взяты в кавычки как строки JSON:

- `user`: пользователь (из forced command его ключа), `from`: адрес клиента (`SSH_CONNECTION`).
- `command`: `ping`, `list`, `images`, `stop`, `remove-check`, `remove`, `start`, `install-image`, `connect` (подключение Positron к контейнеру: строка пишется, когда соединение закрывается, `ms` — его длительность) или `admin-add-user`/`admin-remove-user`.
- `project`; для `start` ещё `revision`, `image` (закреплённое окружение), `positron` (версия Positron клиента), `client` (версия fnkc-ctl клиента; старые клиенты её не передают), `running` (запущенный образ), `created`, `updatePending`; для `install-image` — `image`.
- Для команд администратора: `by` (кто выполнил через sudo), `key` (отпечаток SHA256 ключа, тот же, что sshd пишет в `Accepted publickey for fnkc … SHA256:…`), для `remove-user` — `stopped` и `failed`.
- `ms`, `result` (`ok` или `error`), `error` (текст, который увидел пользователь), `warnings` (предупреждения через ` | `).

По полю `client` видно, все ли перешли на новую версию (пользователь и версия его клиента за две недели):

```
journalctl -t fnkc-ctl --since -14d -o cat | sed -nE 's/^user=([^ ]*) .*command=start .*client=([^ ]*).*/\1 \2/p' | sort -u
```

Журнал хранится столько, сколько настроено в journald; чтобы он переживал перезагрузку, нужен каталог `/var/log/journal` (`Storage=persistent` в `/etc/systemd/journald.conf`).

## Восстановление после сбоев

- Остановка: `docker stop` от агента ждёт до 90 секунд. Остановка не меняет зависимости: намеренные изменения заранее фиксируются командой `fnkc-projects snapshot`.
- Изменение настроек во время работы: сохраните работу, дождитесь окончания заданий, явно остановите проект и откройте снова. Открытие никогда не навязывает обновление поверх работающего задания.
- Неудачная замена остановленного контейнера: инициализация по возможности возвращает предыдущее имя контейнера; тома проекта никогда не удаляются. Если процесс умер во время замены, старый контейнер остаётся под именем `fnkc.recovery.<user>.<project>` (вне имён проектов, с теми же метками владельца) и следующее открытие само восстанавливает его или завершает замену; контейнеры старых версий с именем `<container>-previous` распознаются, только если их метки принадлежат этому проекту. Не запускайте два контейнера с одним томом рабочей копии.
- Блокировки: файлы `*.kernel` не удаляйте. Ядро автоматически освобождает блокировку при завершении процесса; наличие файла не означает занятость. На macOS/Linux нужен Python 3, на Windows используется именованный mutex. При переходе с версий до 0.4 (однократно) закройте сессии и завершите старые процессы до обновления: см. [Lifecycle invariants](lifecycle.md#release-history-and-one-time-migrations).
- Прерванное первое клонирование: `.fnkc-initializing` не даёт считать частичную копию полной. Сделайте резервную копию тома, проверьте, есть ли там работа пользователя, и только потом сбрасывайте одноразовый частичный клон или восстанавливайте из резервной копии. Непустые рабочие копии автоматически не удаляются.
- Откат образа: замените в манифесте рабочей копии дайджест на предыдущий сохранённый, остановите и откройте проект снова. Откат образа не отменяет изменения в файлах проекта или данных; при необходимости восстанавливайте их отдельно.

## Отключение пользователей

Выполните `sudo fnkc-ctl admin remove-user anna`. Команда сначала удаляет ключ пользователя (под общей блокировкой хоста), затем останавливает каждый его работающий контейнер проекта под блокировкой этого проекта: идущее в этот момент открытие либо закончится до остановки, либо откажет при повторной проверке ключа. Если какой-то контейнер остановить не удалось, команда перечисляет его и завершается с ошибкой. Существующие потоки брокера каждые пять секунд перепроверяют подключение пользователя и закрываются при отзыве. Проверьте результат команды: если контейнер остановить не удалось, администратору нужно разобраться дальше. В конце команда перечисляет оставшиеся проекты пользователя и их тома: они хранятся, пока вы не решите. `sudo fnkc-ctl admin projects anna` показывает их и позже. `sudo fnkc-ctl admin remove-project anna <проект>` показывает, есть ли в проекте работа, которой нет в Gitea (неотправленные коммиты, изменённые и новые файлы); с `--delete` проект удаляется, только если такой работы нет. Если она есть, попросите пользователя или коллегу отправить её в Gitea, либо удалите всё равно с `--lose-work`. Отзыв доступа не может вернуть данные или ключи, уже скопированные куда-то ещё; при необходимости смените учётные данные затронутых проектов.

Ведите учёт опубликованных дайджестов окружений, разрешённых URL репозиториев, бюджетов хостов и поддерживаемых версий Positron. После изменений шлюза или OpenSSH повторяйте тесты доступа с двумя пользователями.

Подробные гарантии, ограничения хранения и процедура обновления: [Lifecycle invariants](lifecycle.md).
