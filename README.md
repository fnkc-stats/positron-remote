# FNKC Projects

Воспроизводимый анализ на R в отдельных Docker-контейнерах для каждого пользователя и проекта, в первую очередь на управляемом Linux-сервере. Командная строка и расширение Positron используют один и тот же код. Все бинарные файлы, нужные проекту, включая R-пакеты и сервер Positron, один раз собираются в образ, и проект выбирает его неизменяемый дайджест в `container.json`. Хостам не нужен доступ к Posit, CRAN или реестру образов: если образа на хосте нет, он скачивается на компьютере пользователя, передаётся через шлюз и проверяется хостом. Репозиторий клонируется внутри контейнера.

**В версии 0.3 сервер Positron входит в образ (его больше не скачивают ни хост, ни клиент), а проекты, контейнеры и тома называются по имени репозитория в Gitea. Обновляйте сервер и клиенты одновременно. Контейнеры и тома, созданные версией 0.2 (с хешем в имени), новая версия не использует: запушьте работу, остановите их и удалите после проверки.**

## Быстрый старт

**Аналитикам** (подробности: [инструкция](docs/workflow.md)):

1. Получите у администратора: адрес сервера и отпечаток его SSH-ключа хоста, адрес Gitea и файл расширения `fnkc-projects.vsix`. Отправьте администратору свой **публичный** SSH-ключ (`~/.ssh/id_ed25519.pub`) и добавьте его в свою учётную запись Gitea.
2. Установите Positron той версии, для которой собраны образы ([Версия Positron](#версия-positron)), и в Positron: **Extensions → … → Install from VSIX**, выберите `fnkc-projects.vsix`.
3. Скопируйте [ctl/examples/config.json](ctl/examples/config.json) в `~/.config/fnkc-ctl/config.json` и впишите адреса хоста и Gitea (или задайте их в **Settings → FNKC Projects**).
4. Сверьте ключи хостов с полученными отпечатками, затем выполните `ssh-add` для своего ключа.
5. Выполните **FNKC Projects: Check Setup** из палитры команд и исправьте всё, о чём она сообщит (в том числе выключите автоматические обновления Positron).
6. Выполните **FNKC Projects: Open Project…** и введите имя репозитория, например `thesis`. Первое открытие нового образа на хосте занимает несколько минут, следующие — секунды.
7. Работайте в открывшемся окне. Коммитьте и пушьте как обычно. Закончив, выполните **FNKC Projects: Stop This Project and Close the Window**: при остановке контейнер записывает установленные R-пакеты в `renv.lock` (`renv::snapshot()`); закоммитьте его при следующем открытии.

Новый репозиторий проекта создаётся в Gitea из шаблона нужной версии R: в нём уже есть `container.json` и `renv.lock` ([что настроить администраторам](docs/admin-setup.md)).

**Администраторам**: [сборка и установка](#сборка-и-установка) ниже, затем [руководство оператора](docs/operations.md). **Тем, кто ведёт R-окружение**: [изменение командного образа r-env](docs/r-packages.md#изменение-командного-образа-r-env).

## Архитектура

Локальное расширение/CLI определяет репозиторий и точный начальный коммит; с Gitea на компьютер скачиваются только этот коммит без содержимого файлов и `container.json` (частичный fetch), сам репозиторий клонируется внутри контейнера (`git clone` с переадресацией ssh-agent только на время клонирования). Сервер проверяет права пользователя, разрешённый репозиторий и дайджест образа и постоянную рабочую копию. Для существующей рабочей копии окружение выбирает её собственный `container.json`. Открытие никогда не делает слияние и не переключает существующую ветку автоматически.

У учётной записи шлюза SSH **вся переадресация отключена**. Её принудительная команда (forced command) принимает ограниченные по размеру управляющие запросы и `agent connect <project-id>`. Последняя проверяет, что контейнер принадлежит пользователю, и передаёт поток только на SSH-порт этого контейнера. Адрес или порт назначения вызывающий не задаёт. Клиент закрепляет ключ хоста контейнера, полученный через доверенное управляющее соединение. Перед первым использованием проверьте ключ хоста шлюза.

Проект называется так же, как его репозиторий в Gitea: `muhina-PI-2026-1` — это и строка в списке проектов, и контейнер `fnkc-<user>-muhina-PI-2026-1`, и папка `~/muhina-PI-2026-1` в контейнере. Два репозитория с одинаковым именем (в разных организациях) нельзя открыть на одном хосте одновременно: хост отказывает второму, потому что контейнер и рабочая копия с этим именем принадлежат первому. SSH-псевдонимы включают и хост, и имя проекта. Всегда используйте один канонический URL: хост сравнивает его с URL рабочей копии.

У контейнеров отдельные сети Docker, ограничения памяти, CPU и числа процессов, ротация логов и именованные тома для рабочей копии и состояния Positron. Расширения разделены по проекту, архитектуре и коммиту Positron. Сервер Positron находится в образе и доступен только для чтения. PID 1 контейнера — `docker-init`: он передаёт `docker stop` скрипту запуска, который сначала выполняет `renv::snapshot()`, затем останавливает sshd. Все изменения на хосте, допуск проектов и установка среды выполнения выполняются последовательно через локальную блокировку хоста.

В контейнерах аналитиков выполняется доверенный код команды. У них есть доступ к сети для Git и анализа. Они не являются границей изоляции для недоверенного кода агентов или CI с чувствительными данными.

## Требования и поддерживаемые конфигурации

- Сервер: Linux, Docker Engine, Node.js **22.18+**, OpenSSH с подключаемыми фрагментами конфигурации, systemd. Для диагностики простоя и нехватки памяти (OOM) используйте cgroup v2.
- Клиент: Positron, OpenSSH, Git. Для командной строки нужен Node.js 22.18+. Для интерфейса установите VSIX расширения.
- Образы: нативные linux/amd64 и linux/arm64. Эмуляция не допускается: запуск R из командной строки не доказывает, что Positron/Ark будет работать надёжно.
- macOS: Colima или Docker Desktop. Выбранный движок используется через явный контекст.
- Windows: начальная настройка через x64 WSL2 остаётся экспериментальной до реального пилота. Windows ARM этой настройкой не поддерживается.
- Docker запускается при необходимости; общий демон остаётся работать. Останавливайте его вручную, когда нужно.

## Сборка и установка

```bash
npm ci --prefix ctl
npm --prefix ctl run check
npm --prefix ctl run package
```

Установите `ctl/dist/fnkc-projects.vsix` командой Positron **Install from VSIX**.
Для установки на сервер соберите `npm --prefix ctl run server-bundle`, скопируйте `ctl/dist/fnkc-ctl-server.tar.gz` на сервер, распакуйте и выполните `sudo ./fnkc-ctl-server/install.sh`. Установщик отключает переадресацию на шлюзе, обновляет подключённые ключи, проверяет и перезагружает sshd. Согласуйте миграцию с пользователями: на время обновления существующие сессии нужно закрыть.

Пользователь добавляется командой `sudo fnkc-ctl admin add-user anna /path/to/anna.pub`. У служебной учётной записи есть доступ к Docker; аналитики не получают её оболочку и общую переадресацию. Точные разрешённые репозитории образов и ресурсы задаются в `/etc/fnkc-ctl/agent.json`.

Скопируйте [пример клиентской конфигурации](ctl/examples/config.json) в `~/.config/fnkc-ctl/config.json`. Настройки подключения и учётных данных — личные настройки компьютера; настройки рабочей области репозитория не могут их переопределить. `decryptionHosts` явно перечисляет серверы, на которых можно расшифровывать данные проектов (Docker на этом компьютере разрешён всегда). По умолчанию список пуст. Расшифровка описана в [docs/workflow.md](docs/workflow.md#зашифрованные-данные).

## Окружения проектов

```json
{
  "image": "ghcr.io/fnkc-stats/r-env@sha256:<published-64-hex-digit-manifest-digest>"
}
```

Используйте дайджест из сводки **publish-manifest** workflow образа. Шаблон в репозитории закрепляет уже опубликованный образ amd64; замените его новым проверенным мультиархитектурным дайджестом, когда он появится. Одни теги без дайджеста не принимаются. На сервере разрешаются точные репозитории образов, а не префиксы целой организации.

Сборка сохраняет в `/usr/local/share/r-env` файл `renv.lock`, его контрольную сумму и список установленных пакетов. Она проверяет R и версию каждого зафиксированного пакета (включая рекомендуемые), загружает пространства имён и проверяет Quarto. CI ([image.yml](.github/workflows/image.yml)) нативно собирает обе архитектуры, рендерит синтетический отчёт, запускает [проверки R-окружения](checks/README.md) и интеграционные тесты SSH, всё без сети, и только после этого публикует уникальные теги и общий манифест. Опубликованные дайджесты сохраняют установленное окружение; репозитории apt не являются историческими снимками, поэтому повторная сборка из исходников позже не обязательно даст те же системные пакеты.

`r-env` собирается для R 4.2, 4.5 и 4.6, по одному образу на серию, из `env/versions/<series>/` (версия R, дайджест базового образа Rocker, снимок CRAN и `renv.lock`); все публикуются в один репозиторий. Чтобы добавить пакеты в серию, выполните `env/lock.sh <series> <package>...`: скрипт добавит их и их зависимости в `renv.lock` серии из её снимка CRAN. Для нового патч-релиза R или новых версий пакетов измените `build.args` серии и выполните `env/lock.sh --update <series>`. Одна серия собирается локально командой `env/build.sh <series>`. Прежде чем менять дайджест в каждом проекте отдельным коммитом с ревью, проверьте новый образ: `checks/run.sh <image>` проверяет, что его пакеты совместимы, и выполняет типовые задачи команды на синтетических данных ([checks/README.md](checks/README.md)). Проект из шаблона Gitea хранит `renv.lock` своей серии; первая консоль R восстанавливает его, беря версии из образа, так что ничего не скачивается. Пакет, нужный только в одном проекте, устанавливается в контейнере через `renv::install()` и записывается в `renv.lock` проекта сам при остановке контейнера (`renv::snapshot()`; вручную: `fnkc-projects snapshot`); он сохраняется в `renv/library` на томе рабочей копии, а кеш renv — на томе `<base>-library`. Полный порядок работы и правила для загрузок из CRAN и renv: [docs/r-packages.md](docs/r-packages.md).

Если на хосте нет закреплённого образа, открытие скачивает его по дайджесту на вашем компьютере и передаёт через шлюз, а хост перед загрузкой сверяет каждый слой с дайджестом — один раз для каждой пары хоста и образа. Хосты с доступом к реестру могут скачивать образ сами (`pullImages`). См. [руководство оператора](docs/operations.md#образы-окружения).

Метки образа описывают его содержимое: `r-env.r-version`, `r-env.tidyverse-version`, `r-env.cran-snapshot`, `r-env.quarto-version`, `positron.version` и `positron.commit` (`docker image inspect <образ> --format '{{json .Config.Labels}}'`). В образе также есть git, git-crypt, GnuPG, Quarto и zsh — оболочка пользователя по умолчанию.

## Версия Positron

Сервер Positron собран в образ, а сервер подходит только к той сборке Positron, для которой выпущен. Поэтому вся команда работает в одной версии Positron с выключенными автоматическими обновлениями (Check Setup предлагает выключить их: `update.mode: none`). Сейчас это **2026.11.1-4**; версия записана в [env/positron.args](env/positron.args). Открытие проекта из Positron другой версии хост отклоняет до создания контейнера и сообщает, какая версия нужна.

Переход на новую версию, раз в несколько месяцев:

1. `env/positron.sh` (без аргументов — последний релиз, или `env/positron.sh 2026.11.1-4`) записывает в `env/positron.args` версию, коммит и контрольные суммы серверов для amd64 и arm64.
2. Коммит и pull request: CI собирает образы всех серий R с новым сервером, проверяет, что сервер запускается без сети, и после слияния публикует их.
3. Обновите дайджесты в шаблонах Gitea и в `container.json` проектов, затем все одновременно обновляют Positron до этой версии.

**Другая версия Positron у одного из членов команды.** `container.json` закрепляет образ с сервером Positron команды, и его не нужно менять. Если Positron на компьютере — другая сборка, Open сам ищет в реестре образ того же окружения для неё: той же серии, собранный для этой версии Positron, с той же контрольной суммой `renv.lock` (метка образа `r-env.lock-sha256`), то есть с теми же R-пакетами. Хост запускает его вместо закреплённого и сам проверяет совпадение метки; закреплённый образ ему для этого не нужен. В репозитории ничего не меняется, остальные работают с закреплённым образом.

Если такого образа ещё нет, Open об этом сообщит, и расширение предложит **Build Environment** уже с нужными серией и версией; когда сборка закончится, оно предложит открыть проект. Собирать нужно один раз на серию и версию Positron, следующие проекты той же серии найдут его сами. Из командной строки: `fnkc-ctl build <серия> --positron 2026.07.1-5` (по умолчанию — версия Positron на этом компьютере). Это запуск workflow [env-image.yml](.github/workflows/env-image.yml) с входами `series` и `positron`; сервер этой версии закрепляется в самом запуске. Образ публикуется с тегом `<серия>-positron-<версия>-…`. Нужен `gh`, вошедший в GitHub (`gh auth login`), с правом запускать workflow в репозитории инфраструктуры. Локально: `POSITRON=2026.07.1-5 env/build.sh 4.6`. Образы, собранные до появления метки, так не находятся: для них Open, как раньше, сообщает, какая версия Positron нужна.

## Команды

```bash
node ctl/dist/fnkc-ctl.cjs doctor
node ctl/dist/fnkc-ctl.cjs open thesis --host server
node ctl/dist/fnkc-ctl.cjs open git@gitea.example.lan:stats/thesis.git --host server
node ctl/dist/fnkc-ctl.cjs open thesis --host server --unlock
node ctl/dist/fnkc-ctl.cjs list
node ctl/dist/fnkc-ctl.cjs stop thesis --host server
```

Автоматический выбор берёт только первый хост из настроек. Он никогда незаметно не переключается на ноутбук. Чтобы перенести работу, запушьте изменения и укажите хост явно. Stop принимает имя репозитория (как в списке проектов) или его полный URL.

Внутри проекта:

```bash
fnkc-projects status
fnkc-projects sync              # только fetch: не делает слияние и не переключает ветки
fnkc-projects run Rscript analysis.R
fnkc-projects run quarto render report.qmd
fnkc-projects snapshot          # записать установленные R-пакеты в renv.lock (то же делает остановка контейнера)
fnkc-projects unlock key.asc    # расшифровать вручную (обычно это делает Open): ключ GPG импортируется, файл удаляется из папки
fnkc-projects lock              # блокировка git-crypt; расшифрованные результаты проверяйте отдельно
```

Выключение при простое по умолчанию **0 (отключено)** на сервере и клиенте. Если оператор его включит, обёртка `run` удерживает аренду задания даже во время ожидания ввода-вывода. Явная остановка всё равно завершает всю работу в контейнере. Обычное открытие не блокирует снова ранее расшифрованную рабочую копию. Переадресация агента используется только при инициализации; для обычной работы с Git нужен явно ограниченный ключ или осознанная временная SSH-сессия с переадресацией.

Обновление окружения, ключа или конфигурации не заменяет работающий контейнер. Сохраните работу, дождитесь окончания заданий, явно остановите проект и откройте снова. При замене остановленного контейнера предыдущий сохраняется, пока инициализация нового не завершится успешно; при ошибках тома проекта сохраняются. Файлы вне подключённых каталогов проекта и Positron не сохраняются.

## Проверка

```bash
./lint.sh
npm --prefix ctl run test:ssh   # нужен локальный образ r-env:verified; только одноразовые тестовые данные
# Или укажите в FNKC_TEST_IMAGE другой совместимый локальный образ.
cd ctl && test/e2e.sh [образ]  # сквозная проверка с Docker этого компьютера (по умолчанию — образ шаблона)
```

Тесты покрывают восстановление после сбоев, откат, одновременные открытия, идентичность рабочей копии, выбор ветки и окружения, квоты, а также отказ в доступе и отзыв доступа по SSH. `npm test` проверяет и расширение: на подставном модуле `vscode` (`ctl/test/fake-vscode.ts`) — что его команды и настройки совпадают с `package.json`, и Build Environment от меню до `container.json`.

[`ctl/test/e2e.sh`](ctl/test/e2e.sh) проходит весь путь проекта: вместо Gitea — одноразовый git-сервер в контейнере, вместо сервера команды — одноразовый Linux-контейнер, на который пакет сервера ставится через `install.sh`. Проверяются отказ для другой сборки Positron, открытие на этом компьютере и через шлюз сервера, расшифровка своим ключом GPG, восстановление `renv.lock` из образа, `fnkc-projects lock` и `unlock` с файлом ключа, `admin add-user` и `remove-user`. Скрипт работает с отдельным `HOME`, ваши `~/.ssh`, `~/.gnupg` и `~/.config` не используются, и всё за собой удаляет (`E2E_KEEP=1` оставляет). Сам Positron он не запускает. Рабочий сервер, внешнее хранилище резервных копий, согласования для реальных данных, окно Positron и клиент на Windows ещё требуют приёмочных проверок.
